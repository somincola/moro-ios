# 相册分享与发帖交接

本文记录系统分享入口的交互调整、恢复规则和验收要求。产品目标是：**选择 Moro 后自动打开主应用，将单张或多张图片加入发帖编辑器，由用户决定发布、保存草稿或放弃。**

## 交互调整

| 场景 | 调整前 | 当前约定 |
|---|---|---|
| 相册选择 Moro | 展示图片数量和“保存到草稿”，需要手动切换 App | 自动准备文件并尝试打开 Moro；只显示短暂进度，无图片预览或第二次确认 |
| “保存到草稿”的含义 | 实际只写入导入队列，尚未创建 App 内草稿 | 移除该按钮；草稿操作只在 Moro 编辑器内执行 |
| 主应用处于普通页面 | 返回前台时尝试新建发帖窗 | 收到分享 URL 或回到前台时自动打开编辑器并上传图片 |
| 已有发帖窗 | 跳过导入，当前窗首次出现后不再接收 | 将分享文字和图片追加到当前编辑器，保留原文、原附件、回复或引用目标 |
| 上传失败 | 可能清除整批待导入文件 | 保留未完成的原文件，显示“重试导入 / 丢弃分享（移除待导入图片）” |
| 用户取消编辑 | 与临时导入记录的关系不明确 | 在 Moro 内选择保存草稿、放弃草稿或继续编辑；放弃后不能被迟到的上传响应重新创建 |

发布、排期、ALT 编辑和附件排序沿用 Moro 编辑器现有能力。分享扩展没有发布权限，也不调用 Mastodon 上传接口。

## 图片与冲突规则

- 每次分享接收 1–4 张图片，保持系统输入顺序；不新增视频分享入口。
- 编辑器的附件总数上限取自服务器 `configuration.statuses.max_media_attachments`（标准 Mastodon 为 4，未提供时按 4，最多按 20 处理）。服务器允许更多时，已有 4 张的编辑器可以继续接收一批 4 张；超过 4 张时编辑器逐张显示全部附件，不折叠为“+N”，每张都能删除、重试和编辑 ALT。分享导入在判断空间前会先读取服务器上限，不受编辑器自身加载时机影响。
- 服务器上限不足以放下整批时，提示给出上限，并提供三种处理：移除部分附件后重试、丢弃这次分享，或先发布（或关闭）当前帖子——该批分享不属于当前帖子、不阻止其发布，编辑器关闭后由根入口在新帖子中打开。
- 图片先完整准备到 App Group，再打开主应用。优先使用文件表示，逐张复制到扩展自己的临时目录，再移动临时副本到 App Group，避免第二次完整拷贝；不移动 Photos / provider 的原文件。扩展不解码预览、不同时保留整批图片 Data。
- 文件读取失败时整批准备失败并提示重试；不静默漏图。超过数量上限时拒绝该批，系统也按最大 4 张配置分享入口的可见性。
- 当前编辑器空间不足、已启用投票、正在发布或正在编辑服务器上的旧帖时，不覆盖当前内容，也不截断分享批次。保留待导入文件，用户可解除冲突后重试，或忽略该批。
- 新分享与当前账号一致才导入。无登录快照的分享暂存为未绑定，主应用完成登录后绑定当前账号；之后以恢复草稿的所有权为准，切换账号不得再次认领同一批内容。不自动切换账号。
- 当前编辑器收到多个批次时串行处理。每批使用稳定 ID，文字最多追加一次，已上传的附件不会因重复 URL 或前台事件再次上传。

## 未完成分享与发布校验

“保存草稿”和“发布”使用不同的校验。失败图片有可恢复的暂存原文件时允许保存草稿；失败附件仍然阻止发布。

仅检查编辑器中已有的失败或上传占位还不够：一批 4 张图片在完成第 2 张后被取消时，剩余 2 张可能尚未产生占位。因此发布还必须检查当前草稿关联的共享索引，而不是只检查界面上的附件。

- 整批正在导入，或仍有属于当前草稿的未确认图片时，禁用发布按钮，直接调用发布方法也会被拒绝。不会只发送 `.uploaded` 的子集并清掉剩余图片。
- 新建或恢复编辑器时立即绑定恢复存储；没有绑定、无法加锁或索引无法解码时，分享草稿按“尚未完成”处理，不能把读取失败当成空队列。
- 发布按钮读取编辑器缓存的“待导入”快照，渲染时不触碰跨进程索引锁；快照在绑定存储、恢复草稿、每批导入结束、重试/丢弃以及回到前台时刷新。点击发布时再读一次索引做权威检查，因此一次短暂的锁冲突不会让按钮闪烁，也不会放过漏图发布。
- 索引无法解码是持久状态，不能只靠“稍后重试”：编辑器显示分享提示，“丢弃分享”与删除草稿会修复索引——恢复其余可解码条目、移除当前草稿关联的批次与文件并重写索引（原始损坏内容保留备份），已上传附件不受影响。草稿因此总能被发布、保存或丢弃，不会两头都被锁死。
- 用户可以重试、保存草稿，或明确丢弃待导入图片后再发布已有内容。忽略/丢弃操作写入失败时保留提示和文件，不伪装成成功。
- 即使编辑器暂无正文和可见附件，只要还有待导入的分享，也必须让用户选择保存或放弃，不能依赖失败占位是否被计入 `hasDraftableContent`。

## 文件操作与索引互斥

- App 和扩展都在文件锁外复制、移动及删除图片。只有索引读取、追加、确认、移除属于短暂的临界区；临界区内没有图片处理、网络请求或 `await`。
- 索引锁使用非阻塞获取加有界重试（每 10 ms 一次，最多约 200 ms）。临界区只有几毫秒，App 与扩展的正常交错由重试吸收，不变成用户可见的失败；等待有上限，对端被挂起时也不会无限阻塞。重试耗尽或创建锁失败时记录日志并跳过操作；确认、移除等写操作返回失败，上传进度进入现有重试路径，原文件继续保留。
- 扩展取消时若无法更新索引，会在暂存目录写入 `.cancelled-<UUID>` 墓碑并删除该批文件。App 读取索引时跳过带墓碑的条目，并在锁内清除条目、文件和墓碑；用户已取消的分享不会在之后回到编辑器。
- 扩展遇到无法解析的索引时备份原始数据并从空索引继续，不让一次损坏阻断之后的所有分享。
- 文件全部移动完成后，扩展才发布索引条目。复制前、逐张移动后、提交索引前检查取消；中途取消会清理未完成目录，不发布半批条目。
- 扩展导入 actor 保留刚提交的 ID，避免控制器还没收到 ID 时取消无法找到它；取消标记也阻止尚未开始或仍在等待 provider 的准备任务迟到后写入索引。
- 丢弃草稿先成功移除关联暂存，再移除恢复记录。拿不到锁时保留恢复记录并报错；发布成功后的清理使用已通过“无待导入图片”校验的前提，不重新删除其他批次。

缩短锁范围可以降低挂起时持锁的风险，不等于消除了系统强制终止的所有窗口。文件锁与扩展共享数据的要求见 [Apple TN2408](https://developer.apple.com/library/archive/technotes/tn2408/)。发布前仍须在真机覆盖分享途中取消、切后台和系统终止。

## 打开 App 与接收

```mermaid
flowchart LR
  A[相册选择 Moro] --> B[逐张复制原文件到共享暂存]
  B --> C[打开 moro://share/compose?item=UUID]
  C --> D{已有编辑器}
  D -->|有| E[检查冲突并追加]
  D -->|无| F[创建或恢复编辑器]
  E --> G[串行上传并保存恢复进度]
  F --> G
  G --> H[用户选择发布、保存草稿或放弃]
```

- URL 只含不透明 UUID，不携带正文、账号令牌或文件路径。主应用严格校验 scheme、host、path 和查询参数，从 App Group 读取已暂存内容。
- 编辑器同时监听分享通知和前台事件。根入口在编辑器存在时不再创建第二个编辑器；相机或子 Sheet 覆盖编辑器期间仍保持其接收所有权。
- 打开失败时保留准备好的数据，提供“打开 Moro”重试和手动切换提示；用户明确取消分享时删除该批暂存。

### iOS 平台边界

Apple 没有给 Share Extension 提供可保证的主应用直接启动契约。当前实现沿公开 responder chain 查找 URL opener，调用公开的 `UIApplication.open`，找不到时回退到 `NSExtensionContext.open`；不使用 `UIApplication.shared`、私有 selector 或运行时反射。即使某个系统版本实测成功，也不能据此保证所有宿主、系统版本或审核结果。

这一限制来自 [Apple 的扩展启动说明](https://developer.apple.com/forums/thread/773342)；`NSExtensionContext.open` 的支持范围见 [Apple API 文档](https://developer.apple.com/documentation/foundation/nsextensioncontext/open(_:completionhandler:))。发布前必须用目标 iOS 真机从 Photos 验证；启动失败时，回到 Moro 后仍能接续导入。

## 自动恢复与手动草稿

1. 主应用在消费内容前先保存自动恢复记录，随后逐张处理和上传。
2. 每张图片上传成功后，先将服务器附件 ID 和分享来源 ID 写入恢复记录，再确认并删除该张暂存原文件。
3. 未上传、读取失败或进度持久化失败的文件继续保留。重启或恢复已有草稿时，仅处理剩余文件，并保留已经上传的附件与合并后的文字。
4. 自动恢复记录在草稿列表沿用“自动”分类。只有编辑器中的“保存草稿”操作创建或升级为手动草稿；已有手动草稿仍保持手动分类。手动保存后即使仍有失败附件，也不会因为编辑器关闭或下次回到前台立即重开；从草稿箱恢复时继续处理剩余文件。
5. 发布成功、删除草稿或明确放弃时，按分享来源 ID 清理关联暂存。上传任务取消后即使收到迟到的成功响应，也不得重新创建已放弃的记录。
6. 忽略分享只清理该批剩余文件及失败占位，保留原有编辑内容和已成功上传的附件。
7. 分享恢复记录不替换同账号、同发帖目标下无关的自动草稿。

共享索引沿用原有 `shared_compose_draft_staging_items_v1`，新增草稿来源字段均为可选，兼容旧数据。App 和扩展通过同一文件锁协调索引修改，扩展追加时保留已有条目的未知字段。共享区域不存访问令牌。

当前索引仍由跨进程共享 UserDefaults 承载。进程内回读和 `synchronize()` 不能当作跨进程事务或可靠落盘回执；本轮没有迁移存储格式。后续可迁到与锁文件同目录的 JSON 索引，在锁内读取最新内容并原子替换，同时设计旧索引迁移与回滚；不能只替换一端的存储。

## 验收与验证边界

| 验收项 | 验证方法 |
|---|---|
| 无预览、无“保存到草稿”中间步骤 | Photos 真正调用已安装的 Share Extension |
| 普通页面接收单张 / 多张 | 从系统分享切回主应用，核对数量、顺序及上传状态 |
| 已打开编辑器时仍接收 | 先输入文字和添加附件，再从 Photos 分享，核对追加且不丢原内容 |
| 发布始终由用户确认 | 本地 fixture 统计请求，导入、重试、保存、放弃均不得发出发布请求 |
| 未完成整批不能漏图发布 | 4 张完成 2 张后取消，确认剩余尚无占位也禁止发布；恢复完成后才允许发布 |
| 锁失败不能改变确认状态 | 持有另一把文件锁，验证确认/移除失败、原图和元数据不变、丢弃失败仍保留恢复所有者 |
| 短暂冲突不报错 | 持锁 50 ms 后释放，验证扩展暂存与发布前检查成功；持锁期间发布按钮快照不翻转 |
| 取消必须生效 | 持锁时在扩展取消，验证留下墓碑；App 之后不再提供该批，并清除条目、文件与墓碑 |
| 损坏索引不锁死草稿 | 损坏索引时发布被拒并显示丢弃入口；丢弃或删除草稿后索引修复、其他批次保留、已上传附件保留 |
| 扩展取消不留下半批 | 准备前取消、移动第 1 / 2 张后取消、服务先取消后迟到准备；确认无索引条目及共享残留图片 |
| 大文件操作不持索引锁 | 使用扩展真实 writer，文件移动期间仍可独立获取索引锁，并保留原索引中的未知字段 |
| 失败与数量冲突可恢复 | 模拟第二张上传失败、已有 3 张再收到 2 张，核对原文件保留、重试及忽略 |
| 没有重复导入 / 恢复不丢内容 | 重复 URL、前后台、部分完成后重建模型、文本与附件来源单元测试 |
| 取消后不复活 | 用不响应取消的上传 transport，放弃草稿后返回上传成功，验证不再落盘 |
| 草稿含义准确 | 保存前为自动恢复，明确保存后为手动；放弃后无残留草稿及关联暂存 |
| 内存和平台兼容性 | 真机 4 张大图 / GIF / HEIC、冷启动、不同 iOS 版本、低内存与后台终止 |

自动化入口为 `SharedComposeHandoffTests`、`ShareExtensionStagingTests`、现有分享恢复单元测试及 `SharedComposeImportUITests`。扩展暂存测试编译真实扩展源文件，不复制一套 writer。界面测试使用真实编辑器和本地 transport，不连接真实 Mastodon 服务器；系统分享用例还会实际启动 Photos 与 Share Extension。模拟器结果不替代真机内存、冷启动、iOS 18 / 26 与 App Review 验证。
