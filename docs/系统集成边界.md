# 系统集成边界

本文定义主 App、Share Extension、Widget、Push 与本地持久化之间的数据边界。各目标共享最少数据，不复制完整业务层。

## 目标与职责

| 目标 | 职责 | 不承担 |
|---|---|---|
| `moro` | 会话、网络、页面、Compose、草稿与系统 handoff | 无 |
| `moroShareExtension` | 读取系统分享输入并写入共享 staging | 登录、上传媒体、直接发布 |
| `moroWidgets` | 展示轻量账号快照并发起 App Intent / handoff | 读取 token、直接请求 Mastodon API |
| `moroNotificationService` | 解密 Web Push、改写通知内容、聚合 badge 并刷新相关 Widget | 读取 Mastodon access token、执行常规 API 请求、下载富媒体附件 |

## 数据所有权

- 访问令牌和账号会话由 `AccountSessionStore` / `KeychainService` 所有；App Group 不保存 token。Notification Service 只通过共享 Keychain access group 读取 Web Push 解密密钥。
- App 内草稿与 Share 导入 staging 由 `ComposeDraftStore` 统一承载，但必须区分账号、来源、状态和附件稳定 ID。
- Share Extension 写入可恢复的导入数据并尝试直接打开主 App，无预览或“保存到草稿”中间确认；主 App 负责编辑、媒体处理、上传和发布。已有编辑器接收并追加，保存草稿或放弃均由用户在主 App 内选择。
- Widget 只读取 App Group 中的活动账号、未读计数和受限头像缓存，快照可以过期但不能泄漏凭证。
- Push 注册和服务器订阅由主 App 协调；Notification Service 使用 payload 中的 session 标识对账未读数，主 App 激活后再与服务器状态校准。

## Handoff 约束

1. 外部入口写入目标、时间和必要的轻量参数。
2. 主 App 激活后一次性消费，先解析目标账号，再切换根入口和内部 Route。
3. 过期、重复或无法解析的 handoff 必须安全丢弃并保留当前页面。
4. 消费完成后清理 staging，失败时只保留可恢复数据，不无限重复触发。

分享交接的完整规则见 [相册分享与发帖交接](相册分享与发帖交接.md)。媒体先持久化上传进度，再逐张确认 staging；失败时保留未处理的原文件。自动恢复记录与用户主动保存的手动草稿分开标记。Share Extension 的直接启动受宿主和系统限制，失败时允许重试或手动切换后恢复。

## 安全与生命周期

- App Group identifier 与 entitlements 必须在各目标一致。
- 共享文件与 UserDefaults 只存最小数据，写入采用完整替换或原子策略。
- 账号退出/移除时同步清理其共享快照、草稿索引和未读数据。
- Extension 的时间、内存和网络预算不可作为主流程正确性的前提。
- 日志不得输出 token、OAuth secret、完整请求头或用户草稿正文。
