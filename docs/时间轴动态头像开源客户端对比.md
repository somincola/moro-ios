# 时间轴动态头像：Mastodon iOS 开源客户端对比

核对日期：2026-10-30。用途：为 Moro 时间轴动态头像方案提供源码依据；本次未实施功能。以下是所列提交的代码行为，不代表已对各 App 做过真机性能比较。

## 1. 结论

这些实现没有展示出统一的“离屏立即销毁全部资源”策略。可以确认的做法包括：按设置选择动态或静态 URL、使用成熟图片库、复用显示容器，以及把暂停播放、清理帧缓存、清空图片分别处理。

对 Moro 最有参考价值的是 Metatext／Feditext 使用的 SDWebImage 路径，因为项目已经使用同一套库。Ice Cubes 的 SwiftUI 接入更接近视图结构，但其动画库默认参数不能直接当作低内存配置。

建议保留现有方案方向：离屏立即停播和解绑；动画资源仅在预算允许时短期保留；超时、超额或内存压力时释放。2 秒、2 个、2MiB 是 Moro 的待测初值，在此次核对的头像路径中没有找到这些固定参数的依据。共享播放器和统一帧时钟仍作为实测后的优化项。

## 3. 对比总表

| 客户端 | 头像加载与动画控制 | 暂停、复用与内存管理的已确认行为 | 对 Moro 的意义 |
|---|---|---|---|
| 官方 iOS | `AvatarImageView` 继承 `FLAnimatedImageView`；GIF 数据构建 `FLAnimatedImage` | 换数据时取消请求、重设图片；库根据 window／superview、hidden、alpha 等条件启停；停止显示链路不等于清空动画对象；帧缓存另有容量和内存警告处理 | 生命周期应分层，不能把停播当成释放 |
| Ice Cubes | Nuke `LazyImage` 加载；设置允许且识别为 GIF 时，将原始动画数据交给 Gifu | `GifView.makeUIView` 准备并启动；包装中没有显式离屏停播或 `dismantleUIView`。锁定的 Gifu 默认缓冲参数为 50 帧、默认不缩小动画帧；库把 `stopAnimatingGIF` 和 `prepareForReuse` 分开 | 接入简单；必须额外设计视口控制、动画帧尺寸和预算 |
| Metatext／Feditext | 时间轴使用 `SDAnimatedImageView`；只有 `animateAvatars == .everywhere` 才选择动态 URL；资料页可单独允许 | Feditext 锁定 SDWebImage 5.13.5。库自动启停依据视图层级及自身隐藏状态；默认暂停保留播放器与图片，帧缓存另由配置／内存警告管理；已查列表回调没有头像专用的离屏销毁策略 | 技术栈最接近；Moro 应在库上补充真实视口判断与总预算 |
| Mammoth | 普通 `UIImageView`＋SDWebImage；头像按显示像素缩放、圆角处理；模型可保留已解码头像 | `willDisplay` 复用 `decodedProfilePic`；`prepareForReuse` 取消加载并将 image 置空。所查路径没有头像专用的逐帧播放器或帧预算 | 可借鉴按尺寸处理、缓存命中和复用清理；不能据此证明其动态头像已采用低内存帧管线 |
| tooot | 时间轴把 `avatar`／`avatar_static` 交给 `GracefullyImage`，底层是 Expo Image；Reduce Motion 选择静态 URL | JS 包装中没有头像专用的视口、暂停或销毁控制，交给下层图片组件和列表生命周期；锁定 Expo Image 1.11.0 | 支持设置下的静态替代值得沿用；不能把 JS 无控制代码解释成原生层没有处理 |

## 4. 各实现的关键证据

### 4.1 官方 Mastodon iOS：停播与资源替换分开

`AvatarImageView.configure` 会取消旧请求、重置图片，再加载新头像；GIF 使用单独数据请求创建 `FLAnimatedImage`。URL 检查避免迟到的请求覆盖已经复用的头像。

FLAnimatedImageView 的停播路径暂停显示链路，保留动画对象；设置普通 image 会清掉 animatedImage。FLAnimatedImage 的帧缓存窗口和内存警告响应属于另外一层。这里的可见条件是视图层级等状态，不是头像与滚动视口的几何交集。

- [AvatarImageView](https://github.com/mastodon/mastodon-ios/blob/6d45b164ad2c5b42f07e7296464fe973abc65a12/MastodonSDK/Sources/MastodonUI/View/ImageView/AvatarImageView.swift)
- [FLAnimatedImageView 启停及图片替换](https://github.com/Flipboard/FLAnimatedImage/blob/d4f07b6f164d53c1212c3e54d6460738b1981e9f/FLAnimatedImage/FLAnimatedImageView.m)
- [FLAnimatedImage 帧缓存及内存压力处理](https://github.com/Flipboard/FLAnimatedImage/blob/d4f07b6f164d53c1212c3e54d6460738b1981e9f/FLAnimatedImage/FLAnimatedImage.m)

### 4.2 Ice Cubes：SwiftUI 包装很薄，默认帧预算不小

`AvatarImage` 的 Nuke 请求含 resize processor，但动画分支拿的是 `container.data`，再交给另一个 Gifu 解码器。因此，不能仅凭 Nuke 的 resize 就断定动画各帧已经按头像尺寸解码。

`GifView` 使用默认 `GIFImageView`，在 `makeUIView` 中准备并启动动画，`updateUIView` 为空，没有声明自己的销毁回调。锁文件确认实际使用 Gifu 4.0.1，revision 为 `f19726eaf0dfa4dbce4d3f80293c9d38c2acba53`。

该版本 Gifu 的 `Animator.frameBufferSize` 默认 50、`shouldResizeFrames` 默认 false；暂停仅设置 display link 的暂停状态，`prepareForReuse` 才会停播并清空 frameStore。所查 `GIFImageView`／`Animator`／`GIFAnimatable` 没有自动按滚动视口切换的逻辑。这不能代替运行测量，也不能推出整个 App 的后台播放情况，但足以说明接入包装没有提供 Moro 所需的完整低内存策略。

### 4.3 Metatext／Feditext：直接使用 SDAnimatedImageView

两个项目的时间轴 `StatusView` 都使用 `SDAnimatedImageView`，由 ViewModel 选择动态或静态 URL。Feditext 的账号模型另有 `.profiles` 范围，允许仅资料页使用动态头像。

Feditext 的 SDK 锁定为 5.13.5，revision 为 `318cca556b0489aede0cd98d8d0c7f1408ab7bd6`。该版本 `SDAnimatedImageView` 默认自动播放；`checkPlay` 根据 window、superview、自身 hidden／alpha 启停，并未计算视口比例。`stopAnimating` 默认暂停，只有开启 `clearBufferWhenStopped` 才额外清帧缓存；图片／provider 不会仅因暂停而释放。播放器收到内存警告还会缩减帧缓存。

所查 `StatusView`、列表 `didEndDisplaying` 和 `ImageCacheConfiguration` 没有设置头像专用 warm TTL 或全局动画帧预算。此结论仅覆盖所列路径，不能解释为 SDK 不缓存或不响应内存压力。

Moro 使用的是 5.21.6，存在共享帧池等实现差异，不能直接照搬旧版逐视图清缓存方法；必须保留现有方案对最后一个活跃消费者的判断。

### 4.4 Mammoth：目标尺寸、缓存命中和复用清理

`PostCardProfilePic` 使用普通 `UIImageView`，常规尺寸为 44pt，transformer 按屏幕 scale 缩放并处理圆角。显示时优先使用 `UserCardModel.decodedProfilePic`，加载完成后保存结果，减少重复准备；复用时取消请求、清空视图图片和模型绑定。

这里的复用清理不等于清空所有缓存：已解码图片仍可由用户模型持有，另有模型 `clearCache` 方法。`PostCardCell.didEndDisplay` 明确暂停的是正文／引用视频，没有给头像另建对应控制路径。普通 UIImageView 也不能作为“头像必定静态”的证据；本次不据此推断其 GIF 运行效果或峰值内存。

## 5. 对 Moro 方案的具体影响

1. **复用视图，管理资源。** 跨越视口边界时停播与解绑；不要求反复拆建整个 UIView。图片、解码器、帧缓存、网络任务分别有释放规则。
2. **明确按头像视口控制。** SDK 的 window／superview 判断只能作补充。Moro 的 LazyVStack 和保留页面使其不足以判断真正可见；还要结合当前页、导航覆盖和 scene。
3. **优先控制解码尺寸与总帧数。** 静态图片的 resize 不代表另一个 GIF 解码器会缩小各帧。先证明逐帧输出尺寸和缓冲受限，再讨论 TTL 的 CPU 收益。
4. **短期保留不额外突破预算。** warm 使用已有总预算，新可见头像优先；内存压力或关闭动画时立即回收。SDK 共享内存缓存不能偷偷长期持有已淘汰 provider。
5. **保留设置与静态回退。** 复用现有“播放 GIF”控制，系统策略禁止时使用静态地址；超出预算时自然退回静态。
6. **用对照数据决定进一步复杂度。** 比较立即销毁与短期保留的创建次数、恢复延迟、CPU、内存峰值和滚动卡顿；没有跨 App 真机数据前不作“谁最省内存”排名。

实施边界、预算及验收继续以[时间轴动态头像低内存方案](时间轴动态头像低内存方案.md)为准。
